# Git Flow

Единый процесс для обоих репозиториев:

| Репозиторий | GitHub |
|-------------|--------|
| Frontend (`client/`) | https://github.com/ban4ello/report-documentation |
| Backend (`server/`) | https://github.com/ban4ello/report-documentation-api |

Правила ниже одинаковы для client и server. Для одной задачи заводите **одноимённые** feature-ветки в обоих репозиториях (если меняются и фронт, и API).

---

## Долгоживущие ветки

| Ветка | Назначение | Стенд |
|-------|------------|-------|
| `master` | Стабильный код, готовый к продакшену | **Прод** |
| `staging` | Код, проходящий проверку на тестовом стенде | **Тестовый стенд** |
| `dev` | Интеграция текущих фич (совместная сборка до/параллельно со staging) | Не прод и не тестовый стенд |

Прямые коммиты в `master`, `staging` и `dev` **запрещены** — только через Pull Request.

---

## Схема движения кода

```
master
  │
  ├── feat/my-task  (ветка задачи)
  │         │
  │         ├──► PR → staging     ← тестовый стенд
  │         └──► PR → dev         ← по желанию, для совместной интеграции
  │
  └── в релизный день:
        staging ──PR──► master    ← прод
```

Кратко:

1. Новая задача **всегда** ответвляется от `master`.
2. Готовая фича сливается в **`staging`** (попадает на тестовый стенд).
3. При необходимости ту же фичу можно слить в **`dev`** (интеграция с другими задачами).
4. В **релизный день** `staging` сливается в **`master`** (выкладка на прод).

---

## Именование веток задач

| Префикс | Когда |
|---------|--------|
| `feat/<описание>` | Новая функциональность |
| `fix/<описание>` | Исправление бага |
| `refactor/<описание>` | Рефакторинг без смены поведения |
| `chore/<описание>` | Инфра, зависимости, конфиги |

Примеры: `feat/settings-templates`, `fix/date-filter`, `feat/parent-calculation`.

---

## Работа над задачей

### 1. Создать ветку от `master`

```bash
git checkout master
git pull origin master
git checkout -b feat/my-task
```

### 2. Коммиты и пуш

Пишите понятные сообщения (что / зачем). Пушьте свою ветку:

```bash
git push -u origin feat/my-task
```

Регулярно подтягивайте актуальный `master`, чтобы меньше конфликтов на релизе:

```bash
git fetch origin
git merge origin/master
# или: git rebase origin/master
```

### 3. Выкладка на тестовый стенд

Когда задача готова к проверке на стенде — откройте **PR: `feat/my-task` → `staging`**.

После ревью и merge код оказывается на **тестовом стенде**.

Опционально: **PR: `feat/my-task` → `dev`**, если нужно собрать несколько фич вместе до/вне стенда.

### 4. Релизный день → прод

1. Убедиться, что на `staging` всё проверено.
2. Открыть **PR: `staging` → `master`** (в каждом репозитории, где есть изменения).
3. После merge — деплой **прода** с `master`.
4. При необходимости синхронизировать `dev` с `master` (чтобы интеграционная ветка не отставала):

```bash
git checkout dev
git pull origin dev
git merge origin/master
git push origin dev
```

## Что мержить куда

| Откуда | Куда | Когда |
|--------|------|--------|
| `master` | `feat/…` | Старт задачи |
| `feat/…` | `staging` | Фича готова к тесту на стенде |
| `feat/…` | `dev` | Нужна совместная интеграция (по желанию) |
| `staging` | `master` | Релизный день |
| `master` | `dev` | После релиза — выровнять `dev` |

Не мержить `feat/…` напрямую в `master` в обход `staging` (кроме аварийных хотфиксов — см. ниже).

---

## Хотфиксы на проде

Если чинить нужно сразу на проде:

1. Ветка от `master`: `fix/critical-…`
2. PR → `master` (быстрый выкат на прод)
3. Сразу же PR/cherry-pick той же ветки (или коммита) в `staging` и при необходимости в `dev`, чтобы стенды не разъехались

---

## Чеклист перед релизом

- [ ] Все нужные фичи влиты в `staging` (client и/или server)
- [ ] Проверено на **тестовом стенде**
- [ ] Нет незакрытых критичных багов по релизу
- [ ] PR `staging` → `master` в затронутых репозиториях
- [ ] После релиза `dev` синхронизирован с `master`

---

## Соответствие стендов и веток

| Стенд | Ветка |
|-------|--------|
| Прод | `master` |
| Тестовый стенд | `staging` |

Деплой настраивается на эти ветки (Vercel / Railway / VPS и т.д.) — см. `DEPLOYMENT_GUIDE.md`.
